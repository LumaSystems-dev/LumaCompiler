# Участие в разработке Luma

Документ относится к 0.2.0. [README](README.md), [архитектура](DESIGN.md),
[руководства](docs/README.md), [MIT](LICENSE).
Изменения должны сохранять компактность языка и сопровождаться реальными тестами.

## Подготовка и сборка

Windows, MinGW-w64 g++ с C++17/static в PATH, PowerShell.
Откройте консоль в корне проекта:

```powershell
g++ --version
.\build.bat
.\tests\run_tests.exe
powershell -NoProfile -ExecutionPolicy Bypass -File tests\cli_tests.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests\documentation_tests.ps1
```

Проверяйте коды завершения, не только последние строки вывода.
Unit suite запускается из корня: import/stdlib fixtures используют current_path.
build.bat собирает оба exe заново, без отдельного dependency manager.
Нет настроенного CI/CMake или обязательного Git workflow.
Ветки и небольшие PR — рекомендации, не автоматизированная политика проекта.

## Как добавить тест

Выберите существующий тематический test_*.cpp. TEST автоматически регистрирует
функцию через test.h; используйте CHECK, CHECK_EQ, CHECK_THROWS.
Пример C++:

```cpp
TEST(my_regression) {
    CHECK_EQ(2 + 2, 4);
}
```

Для реального теста прогоняйте Luma-код, не проверяйте только арифметику C++.
Повторно используйте локальные helpers соответствующего тестового файла.
Если добавляете новый C++ файл, включите его в явный список build.bat.
Для runtime-изменения нужны оба бэкенда и serialize/readChunk/VM.
Для builtin: positive, arity через имя и динамическую переменную,
wrong type, boundary, NaN/inf там, где применимо.
Для import: relative/nested/duplicate/cycle/missing/conflict и диагностика.
CLI-проверка использует временные fixtures, UTF-8, закрытый stdin и timeout.

## Как изменить builtin

Реализуйте NativeFn в natives.h, проверяйте requireArity и значения аргументов.
Меняйте builtinDefinitions (включая размер array): она используется
Analyzer и registerBuiltins Interpreter/VM. Нельзя хранить второй независимый
список статических арностей. Не объявляйте внутреннюю функцию приватной,
если runtime не ограничивает доступ. Обновите docs/BUILTINS.md.
Новое глобальное имя может конфликтовать с прежними программами — укажите это.
Не переназначайте builtin ради изменения arity.

## Как изменить stdlib

Сначала попробуйте существующие Luma-конструкции. Native только при доказанной
необходимости; изменение синтаксиса/типов не должно быть побочным эффектом API.
Публичный API держите небольшим, helpers обозначайте префиксом соглашения.
Модули делят глобальные имена и не имеют приватности.
Обновите тесты, docs/STDLIB.md и короткий stdlib/README.md.
Сохраняйте явно описанную byte-модель, диапазоны, seed и EOF-поведение.
Не превращайте текущий RNG в источник криптографических обещаний.

## Как добавить пример и документацию

Используйте examples/, понятное имя и комментарий о назначении.
Для input укажите ожидаемые строки; для отрицательного примера — ожидаемую ошибку.
Добавьте запись в examples/README.md. Не коммитьте созданные .lbc/exe.
Новые неинтерактивные .luma автоматически проверяет documentation_tests.ps1;
новый интерактивный/negative/eval пример требует записи в его конфигурации.

Каждый fenced-блок luma в Markdown проверяется как самостоятельная программа
в копии examples/. Для особенностей используйте комментарий прямо перед блоком:
`<!-- luma-check: root -->` (файл в корне),
`<!-- luma-check: error -->` (исполнение с кодом 65; runtime-ошибка может успешно компилироваться),
`<!-- luma-check: eval -->` (одно выражение) или
`<!-- luma-check: input Ada|21 -->` (строки ввода через |).
Не используйте | внутри отдельной строки такого тестового ввода.
Ссылки должны быть относительными к документу и вести к существующим файлам.
Ожидаемый результат в тексте дополнительно сверяйте с реальным выводом.

## Архитектурные правила и checklist перед PR

- Не меняйте поведение ради совпадения с документацией — сначала исследуйте код.
- Сохраняйте семантику двух бэкендов; известные расхождения не маскируйте.
- Import разворачивается до Analyzer/Compiler; VM не открывает исходные модули.
- Сохраняйте validation до обращения к операндам и размеры до allocation.
- Отрицательные и неисполняемые function bodies тоже требуют проверки.
- Не обещайте sandbox, GC, оптимизированную сборку или stable ABI, которых нет.
- Не меняйте старые тесты только чтобы скрыть регрессию.
- Обновляйте CHANGELOG, API и примеры вместе с намеренным изменением.
- Полная сборка, unit, CLI, docs suite, --version/--help, RPG и stdlib_demo обязательны.
- Проверяйте source → compile → execute и исполнение без исходных fixtures.

В релизные assets exe/.lbc можно включить осознанно, указав runtime/version
и происхождение. В исходном дереве они исключены .gitignore.
Отсутствует автоматически настроенный release workflow: публикация GitHub
и tag выполняются отдельно владельцем, не этим скриптом.
